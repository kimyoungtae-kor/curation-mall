# 프로젝트 결정 기록

이 문서는 긴 대화나 개발 세션이 끝난 뒤에도 같은 기준으로 작업하기 위한 단일 결정 기록이다. 결정이 바뀌면 기존 내용을 지우지 않고 상태와 변경 이유, 날짜를 추가한다.

## 상태 정의

- `결정`: 현재 구현 기준으로 사용한다.
- `미결정`: 조사 또는 검증 후 정해야 한다.
- `재검토`: 특정 조건이 발생하면 다시 판단한다.
- `대체`: 후속 결정으로 더 이상 사용하지 않는다.

## 결정 사항

### D-001 — 프론트엔드 기술

- 상태: 결정
- 결정일: 2026-08-12
- 결정: Next.js + TypeScript를 사용한다.
- 이유: 모바일 우선 반응형 웹과 향후 앱이 사용할 API를 분리하면서, 프론트 생태계와 팀 확장성을 확보한다.
- 구현 원칙: 주문·결제·재고와 같은 핵심 업무 로직은 Next.js에 중복 구현하지 않고 Spring Boot API에 둔다.
- 재검토 조건: 정적 배포 제약이 핵심 요구를 막거나, 팀 구성상 다른 프론트 프레임워크가 명확히 유리할 때.

### D-002 — 백엔드 기술

- 상태: 결정
- 결정일: 2026-08-12
- 결정: Java Spring Boot를 사용한다.
- 이유: 현재 1인 개발자가 가장 익숙한 기술이며 회원·권한·주문·결제·재고의 트랜잭션을 한곳에서 관리하기 좋다.
- 구현 원칙: `/api/v1` REST API와 OpenAPI 문서를 제공하고 도메인별 모듈 경계를 둔 모듈러 모놀리스로 시작한다.
- 재검토 조건: 팀과 트래픽이 커져 독립 배포가 실제로 필요해질 때 일부 도메인만 분리한다. MVP 단계에서 마이크로서비스로 쪼개지 않는다.

### D-003 — 주 데이터베이스

- 상태: 결정
- 결정일: 2026-08-12
- 결정: PostgreSQL을 사용한다.
- 이유: 상품별로 달라지는 속성, 향후 복잡한 조회·정산·분석, 확장 기능을 고려한다. 사용법은 구현 과정에서 학습한다.
- 구현 원칙: 핵심 주문·가격·재고 데이터는 정규화된 컬럼과 테이블로 관리하고, 가변 상품 속성에만 제한적으로 JSONB를 고려한다. 스키마는 Flyway로 버전 관리한다.
- 재검토 조건: 실제 배포 환경이 PostgreSQL을 안정적으로 운영할 수 없고 다른 DB를 이미 안전하게 운영 중이며, 전환 비용보다 운영 위험이 큰 경우.

### D-004 — 인증과 사용자 유형

- 상태: 결정
- 결정일: 2026-08-12
- 결정: 회원가입·로그인과 비회원 주문을 모두 지원한다.
- 이유: 쇼핑몰의 기본 전환 흐름과 재방문 고객 경험을 동시에 시연해야 한다.
- 구현 원칙:
  - 회원 주문은 `user_id`로 연결한다.
  - 비회원 주문은 `user_id`를 비우고 추측하기 어려운 주문 식별자와 추가 검증 정보로 조회한다.
  - 모든 주문은 주문 당시 구매자·수령자·주소·상품명·옵션·가격을 스냅샷으로 저장한다.
  - 고객과 관리자의 권한은 서버에서 분리·검증한다.
- 재검토 조건: 네이티브 앱이나 외부 클라이언트가 본격화되면 토큰 기반 인증 추가 여부를 판단한다.

- 결정일: 2026-08-12

### D-009 — 주문·세션 신뢰성 기준

- 상태: 결정
- 결정일: 2026-08-12
- 결정: 웹 세션은 Spring Session JDBC로 저장하고, 주문 생성과 결제 확인은 각각 멱등성 키로 중복 처리를 막는다. 주문 생성 시 기본 20분 재고 예약을 사용한다.
- 이유: 새로고침·중복 클릭·프로세스 재시작·결제 타임아웃·동시 주문이 있어도 주문, 결제, 재고를 한 번만 일관되게 반영하기 위해서다.
- 구현 원칙: 클라이언트 금액을 신뢰하지 않고 PostgreSQL 제약과 트랜잭션으로 최종 무결성을 보장한다. 예약 시간은 설정으로 변경할 수 있게 한다.
- 재검토 조건: 결제사 정책 또는 실제 트래픽에서 다른 재고 확정 방식이 필요하다는 근거가 생길 때.

- 이유: 공급처 자료가 없어도 개발할 수 있고 레퍼런스 사이트의 상품·이미지·카피 복제 위험을 피하기 위해서다.

- 재검토 조건: 실제 판매 상품, 공급처 계약, 이미지 사용 범위가 확정될 때.

### D-012 — 초기 구현 버전 기준선

- 상태: 결정
- 결정일: 2026-08-12
- 결정: Java 21, Spring Boot 4.1.0, PostgreSQL 17, Next.js 16.3.0, TypeScript strict를 초기 구현 기준선으로 사용한다.
- 이유: 구현 시작 시점의 안정 배포 버전으로 프로젝트를 재현하고, 팀원이 추가돼도 Wrapper와 lockfile로 같은 개발 환경을 사용할 수 있게 하기 위해서다.
- 구현 원칙: Maven Wrapper와 `package-lock.json`을 저장소에 포함한다. 버전은 기능 개발 도중 무조건 따라 올리지 않고 보안 수정, 지원 종료, 배포 환경 호환성을 근거로 별도 검증 후 갱신한다.
- 재검토 조건: 치명적 보안 공지, 사용 버전의 지원 종료, 배포 환경 비호환 또는 필요한 기능의 최소 버전 변경이 발생할 때.

### D-013 — 데모 미디어 제공 방식

- 상태: 결정
- 결정일: 2026-08-12
- 결정: local/test에서는 프로젝트의 `media` 디렉터리를 `StorageService` 뒤에서 읽고 `/media/**`로 제공한다. stage/prod의 최종 영속 저장소는 기존 서버 점검 뒤 결정한다.
- 이유: 공급처 이미지 없이도 공개 카탈로그 흐름을 검증하면서 상품 로직이 특정 클라우드 SDK나 운영체제 경로에 결합되지 않게 하기 위해서다.
- 구현 원칙: DB에는 `storage_key`만 저장한다. 요청 경로 정규화와 실제 경로 검증으로 저장 루트 밖 접근을 차단하고, stage/prod에서는 `MEDIA_STORAGE_ROOT`를 명시한다.
- 재검토 조건: 기존 서버 영속 볼륨, R2 또는 S3 호환 저장소 중 운영안을 선택할 때.

### D-014 — MVP 결제 시연 방식

- 상태: 결정
- 결정일: 2026-08-13
- 결정: 실제 카드 과금 없이 Spring Boot의 `SIMULATED` provider로 승인과 실패를 시연한다.
- 이유: PG 계약·키·환불 정책 없이도 주문·결제·재고 상태를 안정적으로 검증하기 위해서다.
- 구현 원칙: 프론트가 주문을 임의로 완료하지 않고 서버가 주문 금액과 소유권을 검증한다. 주문 생성과 결제 확인은 별도 멱등성 키를 사용하며 성공은 예약을 확정하고 실패·만료는 재고를 한 번만 복원한다. 공통·prod 시뮬레이터 기본값은 `false`, local/test는 `true`, stage는 시연용 환경 변수로 제어한다.
- 재검토 조건: 사업자 정보, PG 계약·테스트 키, 취소·환불 정책, 웹훅 서명 검증과 운영 책임자가 준비될 때.

### D-015 — 현재 관리자 MVP 경계

- 상태: 결정
- 결정일: 2026-08-13
- 결정: 관리자 시연 범위는 상품·옵션·재고·판매 상태, 주문 조회·허용 상태 전이, 홈 7개 섹션·히어로, 회원 목록 API로 고정한다.
- 이유: 핵심 운영 시연을 완성하면서 파일 업로드와 자유도가 큰 전시 편집의 보안·운영 위험을 별도로 다루기 위해서다.
- 구현 원칙: 공개 기획전은 local/test seed와 공개 조회 API로 제공한다. 관리자 이미지 파일 업로드·삭제, 기획전 CRUD·연결 상품, 브랜드·카테고리·동물 종 CRUD, 회원 상세 화면은 Later다.
- 재검토 조건: 실제 상품 이미지 저장소와 운영 담당자의 편집 요구가 확정되거나 해당 기능이 시연 필수로 다시 승인될 때.

### D-016 — 프로필과 데모 seed 격리

- 상태: 결정
- 결정일: 2026-08-13
- 결정: 애플리케이션 공통 설정에서 `local` 프로필을 자동 선택하지 않고 개발 스크립트가 명시적으로 선택한다. 데모 seed는 local/test에만 적용한다.
- 이유: stage/prod에서 데모 계정과 가상 주문이 의도치 않게 생성되거나 시뮬레이터가 운영 기능으로 오인되는 일을 막기 위해서다.
- 구현 원칙: 배포 프로필과 DB·미디어·쿠키 설정은 환경 변수로 명시하며 local/test 데모 자격 증명을 다른 환경에서 재사용하지 않는다.
- 재검토 조건: stage 전용 안전한 bootstrap 또는 별도 시연 데이터 적재 절차가 마련될 때.

### D-017 — 주문 복구 토큰과 상거래 무결성 보강

- 상태: 결정
- 결정일: 2026-08-13
- 결정: 비회원 조회 토큰은 32바이트 이상의 배포 비밀과 주문의 변경 불가능한 멱등성 데이터로 HMAC-SHA256 결정 생성하고 DB에는 SHA-256 해시만 저장한다. 동일 장바구니 행의 주문 생성은 행 잠금·삭제 건수 검증·부분 고유 인덱스로 한 번만 허용하며, 예약 만료 결제는 원자 취소 후 같은 키에도 계속 만료 오류를 반환한다.
- 이유: 첫 주문 응답 유실 뒤에도 같은 키로 조회 토큰을 복구하면서 원문 저장을 피하고, 동시 클릭·네트워크 재시도·스케줄러 경쟁이 주문·재고·결제 상태를 중복 반영하지 못하게 하기 위해서다.
- 구현 원칙: stage/prod는 `GUEST_LOOKUP_TOKEN_SECRET` 미설정 시 fail-fast하며 값을 임의로 회전하지 않는다. 관리자 상품·옵션 수정은 각 행의 `version`을 검증하고 홈 JSON은 섹션별 스키마를 통과한 경우에만 저장한다. 관리자 로그인은 방문자 데이터를 병합하지 않는다.
- 재검토 조건: 비밀 회전 시 다중 키 검증이 필요하거나 실PG·분산 재고·다중 관리자 편집 정책을 도입할 때.

### D-018 — 찜은 고객 회원 전용

- 상태: 결정
- 결정일: 2026-08-13
- 결정: 장바구니는 비회원에게 계속 제공하되 찜 추가·조회·해제는 `CUSTOMER` 역할로 로그인한 회원에게만 제공한다.
- 이유: 여러 기기에서 이어 보는 개인화 목록이라는 찜의 성격을 회원 계정에 명확히 귀속하고, 로그인 동기를 단순하게 설명하기 위해서다.
- 구현 원칙: 비회원 화면은 찜 버튼 대신 원래 상품으로 돌아오는 로그인 안내를 제공하고, 서버도 익명 `401`·비고객 역할 `403`으로 재검증한다. V4 마이그레이션 체크섬 보존을 위해 방문자 찜 컬럼은 즉시 삭제하지 않는다.
- 재검토 조건: 소셜 로그인 또는 임시 찜 공유 기능을 제품 범위에 추가할 때.

### D-019 — 신규 회원가입 데이터 격리

- 상태: 결정
- 결정일: 2026-08-13
- 결정: 신규 회원가입은 같은 브라우저의 방문자 장바구니·과거 방문자 찜을 새 계정으로 이전하지 않고 빈 회원 장바구니·찜으로 시작한다. 방문자 장바구니 병합은 기존 `CUSTOMER` 로그인에만 제공한다.
- 이유: 가입 직후 다른 ID의 항목이 보이는 것으로 오해할 수 있는 자동 승계를 없애고 새 계정의 소유권 경계를 명확히 하기 위해서다.
- 구현 원칙: 가입 성공 시 방문자 활성 장바구니는 `EXPIRED`, 과거 방문자 찜은 삭제한다. 기존 고객 로그인은 방문자 장바구니만 `MERGED` 처리하며 방문자 찜을 회원에게 복사하지 않는다. 가입 실패 때는 방문자 데이터를 보존한다.
- 재검토 조건: 회원가입 화면에서 방문자 장바구니 승계 여부를 사용자가 명시적으로 선택하는 UX와 사업 규칙을 도입할 때.

### D-020 — 단일 EC2 stage Docker Compose 배포 후보

- 상태: 결정, 외부 검증 대기
- 결정일: 2026-08-15
- 결정: 저트래픽 포트폴리오 시연은 기존 AWS EC2 한 대를 `t3a.medium`으로 변경하고 Nginx, Next.js standalone, Spring Boot `stage`, PostgreSQL 17을 Docker Compose로 함께 실행한다. Certbot으로 HTTPS를 발급하고 같은 오리진에서 `/`, `/api/**`, `/media/**`를 제공한다.
- 이유: 취업 준비 기간의 월 비용을 억제하면서 프론트·API·DB·HTTPS·백업을 한 환경에서 설명하고 재현하기 위해서다.
- 구현 원칙: 외부 포트는 80·443과 관리자 IP로 제한한 22만 사용한다. DB·인증서 볼륨을 영속화하고 DB 백업은 EC2 밖에도 복사한다. `local` 프로필과 공개된 identity/order seed는 배포하지 않으며 가상 catalog/merchandising만 수동 적재한다. 시뮬레이션 결제를 실제 결제로 소개하지 않는다. 로그인·회원가입·비회원 조회는 Nginx에서 우선 속도 제한하고 애플리케이션 계층 제한은 Later로 유지한다.
- 검증 조건: 외부 HTTPS의 프론트 → API → PostgreSQL, Secure 쿠키·CSRF, 미디어, 재시작 영속성, 백업·복구, 모바일 접속과 5분 시연을 통과해야 시연 URL로 확정한다.
- 재검토 조건: 실결제 운영, 유의미한 동시 사용자, 단일 장애점 해소, DB 관리 책임 축소 또는 파일 업로드가 필요할 때 관리형 DB·오브젝트 스토리지·분리 배포를 비교한다.

- 완료 조건: 공개 호스트명을 확정하고 DNS, 인증서 자동 갱신과 외부 HTTPS 시연을 검증한다.
