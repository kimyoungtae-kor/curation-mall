# 배포 및 기존 서버 점검 체크리스트

## 1. 목적

최종 배포처는 기존 보유 서버의 상태를 확인한 뒤 결정한다. 로컬 기능 개발과 별개로 2026-08-16~18에 최소 배포 스파이크를 수행해 8월 29일 시연 위험을 조기에 제거한다.

## 2. 절대 원칙

- 기존 서버 조사는 기본적으로 읽기 전용이다.
- 서버 소유자와 용도가 확인되기 전에는 설치, 재시작, 설정 변경, 포트 개방, 컨테이너 생성, 파일 삭제를 하지 않는다.
- 실행 중인 프로세스·컨테이너·데이터베이스·프록시를 임의로 종료하거나 변경하지 않는다.
- 운영 여부가 불명확한 서비스는 운영 서비스로 간주한다.
- 접속 정보, 개인키, 비밀번호, 토큰, 전체 환경변수 값을 문서·스크린샷·Git에 남기지 않는다.
- 변경이 필요한 경우 대상, 영향, 복구 방법, 작업 시간을 기록하고 명시적 승인을 받은 뒤 실행한다.
- 최종 배포처 결정 전에도 빈 앱 수준의 스파이크는 격리된 포트·서브도메인·DB로 수행한다.

## 3. 1단계: 서버별 읽기 전용 인벤토리

각 서버를 A, B, C처럼 임시 식별하고 아래 항목을 표로 기록한다. 비밀 정보는 기록하지 않는다.

### 소유·용도

- [ ] 서버 소유자와 비용 부담 주체
- [ ] 운영/스테이징/개발 용도
- [ ] 현재 사용 중인 서비스와 담당자
- [ ] 장애 허용 범위와 작업 가능 시간
- [ ] 퍼블릭 IP 여부 및 도메인 연결 상태

### 시스템 자원

- [ ] 운영체제와 버전
- [ ] CPU 코어, RAM, 디스크 총량·여유 공간
- [ ] 시스템 시간대와 시간 동기화 상태
- [ ] 최근 재부팅 시각 및 기본 가용성

### 실행 환경

- [ ] Java 버전과 설치 경로
- [ ] Node.js 버전
- [ ] Docker 및 Docker Compose 설치 여부와 버전
- [ ] 실행 중인 프로세스 목록
- [ ] 실행 중인 컨테이너, 이미지, 네트워크, 볼륨 목록
- [ ] systemd 또는 다른 프로세스 관리 방식
- [ ] 예약 작업과 배치 작업 존재 여부

### 네트워크·프록시

- [ ] 현재 LISTEN 포트와 해당 프로세스
- [ ] Nginx, Apache, Caddy 등 리버스 프록시 존재 여부
- [ ] 방화벽 규칙의 개요
- [ ] DNS와 서브도메인 사용 가능 여부
- [ ] TLS 인증서 발급·갱신 방식과 만료일
- [ ] 외부 DB 또는 스토리지로 나가는 연결 제한

### 데이터베이스·데이터

- [ ] PostgreSQL/MySQL 설치 여부와 버전
- [ ] 기존 DB 인스턴스의 용도와 담당자
- [ ] 백업 방식, 주기, 보관 위치, 최근 복구 테스트 여부
- [ ] 새 애플리케이션 전용 DB·계정 생성 가능 여부
- [ ] 데이터 볼륨의 영속화 위치와 디스크 여유

### 운영·보안

- [ ] SSH 접근 정책과 관리자 계정 관리 방식
- [ ] 보안 업데이트 방식
- [ ] 로그 위치와 보존 정책
- [ ] 모니터링·알림 도구 존재 여부
- [ ] 자동 배포 또는 기존 CI/CD 존재 여부
- [ ] 장애 시 연락할 담당자와 복구 책임자

## 4. 읽기 전용 점검 중 금지 작업

다음 작업은 사전 승인 없이 수행하지 않는다.

- 패키지 설치·업데이트·삭제
- 방화벽, SSH, DNS, TLS, Nginx 설정 변경
- 서비스·프로세스·컨테이너 시작, 중지, 재시작
- 포트 개방 또는 포트 매핑 변경
- 데이터베이스 생성·삭제, 스키마 변경, 사용자·권한 변경
- 파일·디렉터리·로그·Docker 리소스 삭제
- 기존 저장소 pull, checkout, reset 또는 배포 실행
- 재부팅, 디스크 정리, 백업 정책 변경

필요한 변경은 별도 작업 계획에 아래를 명시한다.

1. 정확한 대상 서버와 대상 리소스
2. 실행 명령 또는 변경 내용
3. 기존 서비스 영향
4. 사전 백업과 검증 방법
5. 롤백 명령과 책임자
6. 승인자와 작업 시간

## 5. 2단계: 배포 후보 적합성 판정

### 필수 조건

- [ ] 기존 서비스와 분리된 포트·프로세스 또는 컨테이너 사용 가능
- [ ] 시연일까지 안정적인 외부 접속 가능
- [ ] HTTPS 제공 가능
- [ ] Spring Boot가 실행될 Java 또는 Docker 환경
- [ ] PostgreSQL 전용 DB·계정 또는 별도 DB 컨테이너 사용 가능
- [ ] 영속 볼륨과 백업 위치 확보
- [ ] 동적 미디어 경로가 Git checkout 밖의 전용 절대경로이고 백엔드 비루트 UID/GID만 쓸 수 있음
- [ ] 프론트와 API의 환경변수를 안전하게 주입 가능
- [ ] 최소한의 로그 확인과 재시작 절차 존재
- [ ] 담당자 승인과 장애 시 롤백 경로 확보

### 제외 또는 보류 조건

- 기존 운영 서비스의 자원·포트·DB와 충돌한다.
- 소유자, 담당자, 비용, 용도를 확인할 수 없다.
- 남은 디스크나 메모리가 불충분하다.
- 공개 인터넷에서 HTTPS 연결을 만들 수 없다.
- 백업 또는 복구 경로가 없다.
- 서버 변경 권한은 있으나 변경 승인을 받을 수 없다.

## 6. 3단계: 8/16~18 배포 스파이크

### 8/16 — 조사와 계획

- [ ] 후보 서버 인벤토리 완료
- [ ] 기존 서비스와 충돌하지 않는 격리 방식 결정
- [ ] 테스트 서브도메인 또는 임시 접근 주소 결정
- [ ] 필요한 변경 목록과 롤백 계획 작성 및 승인
- [ ] 배포 환경변수 목록만 정의하고 값은 비밀 저장소에 보관

### 8/17 — 백엔드·DB 최소 검증

- [ ] 빈 Spring Boot 앱 또는 `/actuator/health` 배포
- [ ] 애플리케이션 전용 PostgreSQL 연결
- [ ] Flyway 최소 마이그레이션 실행
- [ ] 외부 HTTPS → 리버스 프록시 → Spring Boot 경로 확인
- [ ] 애플리케이션 재시작 후 DB 데이터가 유지되는지 확인
- [ ] 로그에서 비밀번호·토큰·개인정보가 노출되지 않는지 확인

### 8/18 — 프론트·통합 검증과 결정

- [ ] Next.js 시연 빌드 배포
- [ ] 브라우저에서 프론트 → API 요청 성공
- [ ] CORS, 쿠키, SameSite, Secure 설정 검증
- [ ] 모바일 네트워크에서 외부 링크 접속
- [ ] 배포·재시작·롤백 절차를 다른 세션에서 재현
- [ ] 기존 서버, Cloudflare 조합, 또는 다른 대체안 중 최종안 기록

스파이크가 실패하면 같은 구조를 붙잡고 8/19 이후까지 조사하지 않는다. 실패 원인을 기록하고 격리 가능한 다른 서버 또는 단순한 대체 배포안으로 전환한다.

## 7. 배포 구조 선택 체크

### 선택안 A — 기존 서버에 프론트·백엔드·DB 배포

- 장점: 한 서버에서 관리 가능, 외부 서비스 비용 최소화
- 주의: 단일 장애점, 자원 경합, DB 백업 책임 증가
- 적합 조건: Docker Compose 또는 명확한 프로세스 격리, HTTPS, 백업이 가능함

### 선택안 B — 프론트 정적 자산은 Cloudflare, API·DB는 기존 서버

- 장점: 프론트 전송 부담 감소, 외부 링크 제공이 쉬움
- 주의: SSR 지원 범위, API CORS·쿠키·도메인 설정을 조기에 검증해야 함
- 적합 조건: 프론트를 정적으로 운영할 수 있거나 Cloudflare 실행 환경을 별도 검증함

### 선택안 C — 관리형 또는 별도 임시 환경

- 장점: 기존 서버 충돌 위험 감소
- 주의: 비용, 계정, 데이터 이전, 서비스별 제한 확인 필요
- 사용 조건: 기존 서버가 8/18 게이트를 통과하지 못하거나 승인받을 수 없음

## 8. 출시 전 체크리스트

### 빌드·설정

- [ ] 운영 프로필로 프론트와 백엔드 빌드 성공
- [ ] 개발용 URL, 테스트 계정, 디버그 설정 제거 또는 분리
- [ ] 모든 비밀값이 환경변수/비밀 저장소에서 주입됨
- [ ] 운영 DB에서 `ddl-auto=update` 또는 `create`를 사용하지 않음
- [ ] Flyway 마이그레이션 버전과 적용 결과 확인

### 네트워크·보안

- [ ] HTTPS 강제 및 인증서 자동 갱신 확인
- [ ] 허용된 Origin만 CORS에 등록
- [ ] 세션 쿠키에 HttpOnly, Secure, 적절한 SameSite 적용
- [ ] 관리자 API에 서버 측 권한 검사 적용
- [ ] 회원·비회원 주문 조회에 추측하기 어려운 식별자와 추가 검증 적용
- [ ] 업로드 파일 크기·실제 형식·MIME·픽셀 크기 검증과 서버 생성 파일명 적용
- [ ] `MEDIA_HOST_PATH`의 소유권·mode·여유 공간, 재배포 후 조회와 외부 미디어 백업 확인
- [ ] 공개 응답과 로그에 비밀값·비밀번호·결제정보가 없음

### 데이터·결제

- [ ] 상품 가격과 주문 합계를 서버에서 재계산
- [ ] 결제 요청/승인 금액과 서버 주문 금액 비교
- [ ] 주문 당시 상품명·가격·옵션·배송지 스냅샷 저장
- [ ] 중복 결제 승인과 중복 주문 요청 방지
- [ ] 시연용 결제임을 화면에서 명확히 표시
- [ ] 데이터베이스 백업 생성 및 복구 절차 확인

### 운영·시연

- [ ] 헬스 체크 URL 정상
- [ ] 프론트·백엔드·DB 재시작 순서 문서화
- [ ] 애플리케이션·프록시·DB 로그 위치 확인
- [ ] 데모 관리자/회원 계정 준비
- [ ] 비회원 주문 조회용 데모 정보 준비
- [ ] 모바일과 데스크톱에서 5분 시나리오 2회 연속 성공
- [ ] 시연 직전 DB dump와 `MEDIA_HOST_PATH` 이미지 압축본·체크섬을 서버 밖에 백업

## 9. 장애와 롤백

- 애플리케이션 배포본은 최소 직전 정상 버전 하나를 보존한다.
- DB 마이그레이션은 되돌림보다 전진 수정이 가능한 작은 변경으로 작성한다.
- 파괴적 스키마 변경은 시연 후로 미룬다.
- 롤백 시 애플리케이션 버전과 DB 호환성을 함께 확인한다.
- 장애 발생 시 기능 추가를 중단하고 홈 → 상세 → 주문 → 관리자 확인 순으로 복구한다.
