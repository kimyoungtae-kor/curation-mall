# MVP 완성까지 실행 가이드

기준일: 2026-08-12  
완료 목표일: 2026-08-29

이 문서는 기획 완료 후 실제 구현을 어디서 시작하고 어떤 순서로 끝낼지 정한 작업 지침이다. 여기서 `완성`은 사업 관계자가 외부 HTTPS 링크에서 회원·비회원 구매와 관리자 운영을 직접 확인할 수 있는 **작동형 시연 MVP 완성**을 뜻한다. 실결제 운영, 앱스토어 출시, 공급처 자동 연동은 별도 운영 전환 단계다.

## 1. 최종 완료 상태

8월 29일에는 다음 흐름이 모두 연결돼야 한다.

```text
홈/기획전
  → 상품 목록/상세
  → 찜/장바구니
  → 회원가입·로그인 또는 비회원 주문
  → 서버 가격·재고 검증
  → 테스트 결제
  → 주문 완료/조회
  → 관리자 주문 확인·상태 변경
  → 관리자 상품/기획전 수정
  → 고객 화면 반영
```

기능이 존재하는 것만으로는 완료가 아니다. 프론트엔드, Spring Boot API, PostgreSQL, 이미지 저장소가 실제로 연결되고 새로고침·재로그인·재배포 후에도 데이터가 유지돼야 한다.

## 3. 저장소 기본 구조

서로 다른 생태계를 한 저장소에서 관리하되 배포 단위는 분리한다.

```text
pet-curation-mall/
├─ frontend/                 Next.js + TypeScript
├─ backend/                  Java Spring Boot
├─ infra/
│  ├─ compose.yaml           로컬 PostgreSQL 등
│  └─ nginx/                 배포안 확정 후 프록시 설정
├─ docs/                     기획·설계·진행 문서
├─ .env.example              이름과 설명만, 실제 비밀값 금지
└─ README.md
```

한 저장소를 사용하더라도 Next.js가 PostgreSQL에 직접 접근하지 않는다. 모든 업무 API는 Spring Boot의 `/api/v1` 아래에 둔다.

현재 작업 폴더는 Git 저장소이며 `.gitignore`와 `.env.example`이 준비돼 있다. 실제 비밀번호·키·서버 접속정보가 제외됐는지 확인한 뒤 기능 단위 체크포인트를 남긴다.

### 백엔드 모듈 구조

```text
backend/src/main/java/.../
├─ common
├─ identity
├─ catalog
├─ merchandising
├─ cart
├─ order
├─ payment
├─ admin
└─ storage
```

각 업무 모듈은 필요에 따라 `api`, `application`, `domain`, `infrastructure`로 나눈다. 컨트롤러가 JPA 저장소를 직접 호출하지 않고 애플리케이션 서비스가 트랜잭션과 규칙을 담당한다.

### 프론트엔드 구조

```text
frontend/src/
├─ app/                      라우트와 레이아웃
├─ features/                 auth, catalog, cart, order, admin 등
├─ components/               공통 UI
├─ lib/api/                  Spring API 클라이언트
├─ lib/auth/                 현재 사용자·CSRF 처리
├─ styles/                   토큰과 전역 스타일
└─ types/                    API 타입
```

전역 상태 저장소를 먼저 도입하지 않는다. 현재 서버 데이터는 공용 fetch 클라이언트와 필요한 화면의 React 상태로 관리한다. 장바구니·찜의 원본은 Spring API와 DB다.

프론트 구현의 기본 선택은 다음과 같다.

- 공개 홈·기획전·상품은 Next.js Server Component 중심
- 옵션 선택·슬라이드·찜·장바구니·폼은 필요한 범위만 Client Component
- 서버 상태는 공용 API 클라이언트와 `AuthProvider`, 화면별 React 상태로 관리
- 슬라이드는 직접 구현한 접근성 제어·5초 타이머·교차 전환 사용
- API 타입은 `08_API_CONTRACT.md`와 백엔드 DTO를 대조해 TypeScript로 명시
- 필터·정렬·페이지는 URL query string으로 보존
- 장바구니·찜·개인정보는 `localStorage`를 원본으로 사용하지 않음
- Redux/Zustand, 자유형 페이지 빌더, 오프라인 주문은 MVP에 도입하지 않음

### API 공통 규칙

- 성공과 실패의 HTTP 상태 코드를 구분한다.
- 검증 실패는 필드별 오류 코드를 내려준다.
- 금액은 원 단위 정수로 주고받는다.
- 날짜·시간은 ISO 8601로 주고받는다.
- 페이지 목록은 동일한 페이지네이션 형식을 사용한다.
- 내부 예외 메시지, SQL, 스택 트레이스를 고객 응답에 노출하지 않는다.
- JPA Entity를 그대로 JSON 응답으로 사용하지 않는다.

### 완료 조건

- 화면마다 호출할 API가 식별돼 있다.
- 회원·비회원 주문 소유권과 조회 방법이 모호하지 않다.
- 가격·배송비·재고·결제 상태의 최종 책임이 Spring Boot로 명시돼 있다.
- 8월 14일 이후 새 Must는 기존 Must와 교체해야 한다.

## 6. 단계 1 — 로컬 개발 기반 구축

코드를 만들기 전에 Git 초기화, 비밀값 제외 규칙, 첫 기준 커밋을 끝낸다. 이후 모든 단계는 작은 커밋 단위로 되돌릴 수 있게 진행한다.

### 6.1 백엔드 초기화

Spring Boot 프로젝트에 최소 다음 기능을 추가한다.

- Spring Web
- Bean Validation
- Spring Data JPA
- Spring Security
- Spring Session JDBC
- PostgreSQL Driver
- Flyway
- Actuator
- 명시적 DTO와 Problem Details 오류 계약
- Testcontainers PostgreSQL

프로필은 `local`, `stage`, `prod`로 분리한다. JPA는 `ddl-auto=validate`, Flyway만 스키마를 변경하도록 한다.

가장 먼저 구현할 API는 다음 두 개다.

```text
GET /api/v1/health
GET /api/v1/catalog/products?limit=...
```

### 6.2 PostgreSQL 초기화

로컬 PostgreSQL은 Docker Compose로 실행한다. 애플리케이션용 DB와 계정을 사용하고, 실제 비밀번호는 Git에 올리지 않는다.

초기 Flyway 순서:

```text
V1__create_identity.sql
V2__create_catalog.sql
V3__create_merchandising.sql
V4__create_cart_and_wishlist.sql
V5__create_orders_and_payments.sql
V6__harden_commerce_integrity.sql
```

모든 파일을 첫날 한꺼번에 완성하지 않는다. 각 세로 기능을 구현하기 직전에 해당 마이그레이션을 추가하고 실제 PostgreSQL 통합 테스트를 작성한다.

### 6.3 프론트엔드 초기화

- Next.js App Router와 TypeScript strict 모드
- ESLint와 일관된 포맷 설정
- API 기준 URL 환경변수
- `credentials: include`가 적용된 공통 API 클라이언트
- 공통 오류·로딩 처리
- 모바일 우선 디자인 토큰
- 고객 레이아웃과 관리자 레이아웃 분리

초기 디자인 토큰은 색상, 배경, 텍스트, 간격, 모서리, 그림자, 최대 콘텐츠 폭만 정의한다. 페이지마다 임의 색상과 간격을 만들지 않는다.

### 6.4 첫 세로 연결

1. PostgreSQL seed에 상품 한 개를 넣는다.
2. Spring API가 상품을 조회한다.
3. Next.js 홈에서 API를 호출해 상품명을 표시한다.
4. 프론트·백엔드 테스트와 빌드가 성공한다.

최소 CI 또는 동일한 로컬 검증 명령에는 프론트 typecheck·lint·test·production build, 백엔드 test·build, Flyway validate가 포함돼야 한다.

### 완료 조건

- 새 환경에서 안내 문서만 보고 세 서비스가 실행된다.
- 프론트 → Spring → PostgreSQL 요청이 성공한다.
- Flyway를 다시 실행해도 중복 생성 오류가 없다.
- 비밀정보가 Git과 로그에 노출되지 않는다.

## 7. 단계 2 — 중간 배포 스파이크

기능이 거의 끝난 뒤 처음 배포하면 안 된다. `06_DEPLOYMENT_CHECKLIST.md`에 따라 기존 서버를 읽기 전용으로 조사한다.

### 8/16~18 검증 순서

1. 서버별 소유자, 실행 서비스, 포트, Docker, Java, Node, DB, Nginx, HTTPS, 백업 상태를 확인한다.
2. 승인 전에는 설치·재시작·포트 개방·DB 생성을 하지 않는다.
3. 승인된 격리 환경에 Spring 헬스 체크를 배포한다.
4. 전용 PostgreSQL에서 최소 Flyway를 실행한다.
5. Next.js 빈 화면을 배포하고 브라우저에서 API를 호출한다.
6. HTTPS, 쿠키, CSRF, CORS, 재시작 후 데이터 유지, 롤백을 확인한다.
7. 기존 서버 통합 배포와 Cloudflare 프론트 분리 배포 중 최종안을 기록한다.

기존 서버가 안전하게 사용 가능하면 다음과 같은 동일 출처 구조를 1순위로 한다.

```text
외부 HTTPS
  → Nginx
      ├─ /        → Next.js
      └─ /api/v1  → Spring Boot
                         → PostgreSQL
```

이 구조는 브라우저 세션 쿠키, CSRF, CORS 설정을 단순하게 만든다. 기존 Nginx나 80/443 포트를 임의로 덮어쓰지 않고 승인된 별도 upstream과 배포 디렉터리를 사용한다. 프론트와 API를 서로 다른 도메인으로 분리하는 안은 8월 18일까지 실제 브라우저에서 로그인, 새로고침 후 세션 유지, CSRF 상태 변경 요청까지 통과할 때만 채택한다.

### 완료 조건

- 외부 HTTPS 주소가 있다.
- 프론트 → API → DB 요청이 실제 배포 환경에서 성공한다.
- 배포와 롤백 절차가 문서화돼 있다.
- 실패한 경우 8월 18일에 대체 배포안을 확정한다.

## 8. 단계 3 — 상품 발견과 상세 구매 준비

### 백엔드

- 브랜드, 동물 종, 카테고리, 상품, 옵션, 이미지, 기획전 조회
- 판매 중·품절·숨김 상태 처리
- 상품 목록 페이지네이션과 최소 필터
- 슬러그 기반 상품·기획전 상세
- 홈 섹션 데이터 조회
- 관리자용이 아닌 공개 응답에서는 원가·공급처 내부정보 제외

주요 공개 API 예시:

```text
GET /api/v1/home
GET /api/v1/catalog/products
GET /api/v1/catalog/products/{slug}
GET /api/v1/collections
GET /api/v1/collections/{slug}
```

현재 공개 브랜드·카테고리·동물 종 전용 목록 API는 구현하지 않았다. 홈·상품 응답에 필요한 요약 정보가 포함되고 관리자 상품 편집용 참조 목록은 `/api/v1/admin/brands`, `/categories`, `/species`로 제공한다. 공개 전용 목록이 실제 프론트 요구가 되면 별도 API와 통합 테스트를 추가한다.

### 프론트엔드

- 공지 바와 반응형 헤더
- 최대 3장 히어로 슬라이드
- 상황별 기획전
- 인기·신상품 슬라이더
- 동물·카테고리·브랜드 탐색
- 공간 중심 라이프스타일 콘텐츠
- 상품 목록 2열/4열 그리드
- 상품 상세 이미지, 옵션, 가격, 재고, 설명
- 모바일 하단 구매 CTA

### 테스트

- 숨김 상품은 공개 API에서 조회되지 않는다.
- 품절 옵션은 구매 CTA가 비활성화된다.
- 잘못된 슬러그는 안전한 404를 반환한다.
- 히어로는 키보드 조작과 일시정지가 가능하다.
- 모바일 360px에서 가로 스크롤이 생기지 않는다.

### 완료 조건

- 더미 배열이 아니라 PostgreSQL 상품으로 홈→기획전→상세를 이동한다.
- 상품 옵션을 선택하면 해당 가격·재고가 일관되게 표시된다.
- 로딩·빈 상태·오류 상태가 존재한다.

## 9. 단계 4 — 회원, 방문자, 찜, 장바구니

### 인증 API

```text
POST /api/v1/auth/signup
POST /api/v1/auth/login
POST /api/v1/auth/logout
GET  /api/v1/auth/me
GET  /api/v1/auth/csrf
```

- 이메일을 정규화하고 중복 가입을 차단한다.
- 비밀번호는 Spring PasswordEncoder로 해시한다.
- 세션 쿠키는 HttpOnly, 운영 HTTPS에서는 Secure를 사용한다.
- 상태 변경 요청은 CSRF를 검증한다.
- 로그인 성공 후 세션 ID를 교체한다.
- 관리자 권한은 화면이 아니라 서버에서 검사한다.

### 방문자와 장바구니 API

```text
GET    /api/v1/cart
POST   /api/v1/cart/items
PATCH  /api/v1/cart/items/{itemId}
DELETE /api/v1/cart/items/{itemId}
GET    /api/v1/wishlist
POST   /api/v1/wishlist/{productId}
DELETE /api/v1/wishlist/{productId}
```

- 비회원에게 무작위 방문자 쿠키를 발급하고 DB에는 해시만 저장한다.
- 회원과 방문자는 각각 활성 장바구니 하나만 가진다.
- 기존 `CUSTOMER` 로그인 성공 시 방문자 장바구니를 트랜잭션으로 병합한다. 신규 회원가입은 방문자 장바구니를 만료하고 빈 회원 장바구니·찜으로 시작한다. 찜은 회원 전용이며 방문자 찜을 병합하지 않는다.
- 관리자 로그인은 방문자 장바구니를 병합하거나 소비하지 않는다.
- 같은 옵션 수량은 합치고 현재 재고·구매 제한을 초과하면 조정 사실을 응답한다.
- 장바구니에 담긴 가격을 결제 금액으로 신뢰하지 않는다.

### 완료 조건

- 비로그인 상태에서 담은 상품이 새로고침 후 유지된다.
- 기존 고객 로그인 후 방문자 장바구니 상품이 유지되고, 신규 가입 회원은 빈 장바구니·찜으로 시작한다.
- 다른 방문자·회원의 장바구니 또는 다른 회원의 찜에 접근할 수 없다.
- 로그아웃 후 회원 전용 데이터가 노출되지 않는다.

## 10. 단계 5 — 회원·비회원 주문과 테스트 결제

### 주문 생성 원칙

1. 서버가 장바구니 옵션을 다시 조회한다.
2. 판매 상태, 현재 가격, 재고를 검증한다.
3. 상품 합계, 할인, 배송비, 최종 금액을 계산한다.
4. 구매자·배송지·상품·옵션·가격 스냅샷을 저장한다.
5. 회원 주문은 `user_id`, 비회원 주문은 조회 토큰 해시를 저장한다.
6. 결제 준비 레코드와 멱등성 키를 만든다.

주문 생성 API는 `Idempotency-Key` 헤더를 필수로 받는다. 같은 키와 같은 요청은 기존 주문을 반환하고 같은 키의 다른 요청은 `409 Conflict`로 거부한다. 비회원 조회 토큰은 같은 키의 첫 응답과 재응답에서 동일하게 반환되며 DB에는 해시만 남는다.

주요 API 예시:

```text
POST /api/v1/orders/quote
POST /api/v1/orders
GET  /api/v1/orders
GET  /api/v1/orders/{orderNumber}
POST /api/v1/guest-orders/lookup
POST /api/v1/payments/confirm
POST /api/v1/payments/webhooks/{provider}
```

### 비회원 주문

- 회원가입을 강제하지 않는다.
- 주문 완료 화면에서 주문번호와 조회 토큰을 안내한다. 첫 응답을 잃어도 같은 주문 멱등성 키로 재시도하면 같은 조회 토큰을 다시 받는다.
- 주문번호만으로 개인정보를 조회할 수 없게 한다.
- 조회 실패 반복에 속도 제한을 둔다.
- 이메일·전화번호가 같아도 회원에게 자동 귀속하지 않는다.

### 결제

- 브라우저에는 테스트 클라이언트 키만 둔다.
- 결제 시크릿 키와 승인 API 호출은 Spring Boot에만 둔다.
- 결제사 금액, 주문번호, 결제키를 서버 주문과 비교한다.
- 같은 멱등성 키·결제키가 반복돼도 한 번만 승인·반영한다.
- 예약 만료 결제는 주문·결제 취소와 재고 복원을 원자적으로 처리하고, 같은 키 재요청에도 계속 `409 ORDER_RESERVATION_EXPIRED`를 반환한다.
- 웹훅과 성공 리다이렉트가 다른 순서로 도착해도 같은 결제 서비스로 처리한다.
- 타임아웃 시 무조건 재승인하지 않고 결제 조회 후 복구한다.

결제사 준비가 8월 20일까지 끝나지 않으면 `PaymentGateway` 인터페이스 뒤에 서버 측 테스트 결제 시뮬레이터를 둔다. 이 경우에도 프론트가 주문 상태를 직접 완료로 바꾸지 않고 Spring Boot가 `READY → APPROVED/FAILED` 전이를 처리하며, 화면에 실제 청구가 없는 시연용 결제임을 명확히 표시한다.

### 재고 정책

기본 구현은 주문 생성 시 20분 예약을 만들고, 결제 성공 시 확정하며, 실패·취소·만료 시 한 번만 재고를 복원하는 것이다. 주문 생성은 장바구니 행을 `FOR UPDATE`로 잠그고 삭제 건수를 확인하며, V6 부분 고유 인덱스로 같은 장바구니 행의 이중 주문을 차단한다. 옵션 행의 조건부 재고 갱신으로 재고가 음수가 되지 않게 하고 승인과 만료 처리가 경쟁해도 한쪽만 성공하게 한다.

### 완료 조건

- 회원과 비회원이 각각 테스트 결제 완료까지 통과한다.
- 브라우저에서 가격을 변조해도 서버 주문 금액이 변하지 않는다.
- 동일 결제 확인 요청을 두 번 보내도 결제·재고가 한 번만 반영된다.
- 회원은 본인 주문만, 비회원은 올바른 조회 정보가 있는 주문만 본다.
- 관리자에서 주문과 결제 상태를 확인할 수 있다.

## 11. 단계 6 — 관리자 운영 기능

관리자 UI는 고객 앱과 같은 Next.js 프로젝트 안에 두되 별도 레이아웃과 권한 가드를 사용한다.

### 관리자 API와 화면

```text
/admin/products              상품 목록·등록·수정
/admin/home-sections         고정 홈 슬롯
/admin/orders                주문 목록·상세·상태 변경
```

기획전 CRUD와 회원 상세 관리자 화면은 현재 Later다. 백엔드는 관리자 회원 목록·구매 요약 API만 제공한다.

백엔드 API는 `/api/v1/admin/**`로 분리하고 모든 요청에서 `ADMIN` 권한을 재확인한다.

### 필수 기능

- 상품 기본정보·분류·옵션·가격·재고·판매상태 CRUD
- PC 파일 선택기·모바일 사진 선택기를 이용한 이미지 업로드와 미리보기·대체 텍스트·대표 순서 편집
- 히어로 최대 3장과 고정 홈 슬롯 관리
- 주문 검색·상세·결제 확인
- 허용된 주문 상태 전이
- 회원 기본 목록과 주문 연결

이미지 물리 삭제와 미참조 파일 자동 정리, 기획전 CRUD와 분류 CRUD는 Later로 관리한다. 이미 서버에 저장된 신뢰 가능한 키의 보조 연결 입력은 유지한다.

자유형 페이지 빌더, 대시보드 차트, 다중 관리자 세부 권한은 만들지 않는다.

### 완료 조건

- 관리자가 상품을 수정하면 고객 화면에 반영된다.
- 숨김·판매 종료 상품으로 새 주문을 만들 수 없다.
- 잘못된 주문 상태 전이는 API에서 거부된다.
- 일반 회원이 관리자 URL과 API에 접근할 수 없다.
- `PUBLISHED` 상품은 실제 저장된 이미지가 한 장 이상이고 업로드 파일은 권한·CSRF·형식·용량·해상도 검증을 통과한다.
- 이미지 저장소 구현을 교체해도 상품 업무 코드는 바뀌지 않는다.

## 12. 단계 7 — 기능 동결과 데모 콘텐츠

8월 26일부터 새 기능을 추가하지 않는다.

### 입력할 데모 데이터

- 강아지·고양이 상품 24개
- 옵션 26개와 브랜드 4개
- 옵션과 재고가 있는 상품
- 품절 옵션 상품 1개 이상
- 상황별 기획전 3개
- 히어로 배너 최대 3개
- 공간 중심 라이프스타일 콘텐츠
- 회원·비회원 완료 주문
- 테스트 관리자·회원 계정

이미지는 직접 제작했거나 사용 권한이 확인된 자료만 사용한다. 레퍼런스 사이트 이미지를 내려받아 그대로 사용하지 않는다.

Must가 모두 끝나고 시간이 남을 때만 최소 PWA 범위를 적용한다. 웹 매니페스트, 192px·512px 아이콘, 테마 색상, 설치형 표시까지만 검증하며 PWA 미적용은 MVP No-Go 사유가 아니다. 서비스 워커를 추가하더라도 API·관리자·주문·결제 응답은 캐시하지 않으며 오프라인 구매는 구현하지 않는다.

### 범위가 밀렸을 때 제거 순서

1. 장식성 애니메이션
2. 슬라이드와 기획전 개수
3. 고급 검색·필터·정렬
4. 관리자 대시보드 통계
5. 배너 예약 공개
6. 다중 이미지 편집 편의 기능

회원·비회원 주문, 서버 가격 계산, DB 저장, 관리자 권한, 주문 조회는 제거하지 않는다.

## 13. 단계 8 — 테스트, 보안, 배포

### 백엔드 테스트

- 단위: 금액 계산, 배송비, 장바구니 병합, 주문 상태 전이
- 통합: PostgreSQL 제약, Flyway, JPA 쿼리, 재고 동시성
- 보안: 회원·관리자 권한, 타인 주문 접근, CSRF
- 외부 연동: 결제 성공·실패·타임아웃·중복 웹훅

### 프론트엔드 테스트

- 컴포넌트: 옵션 선택, 수량, 폼 검증, 오류 표시
- 접근성: 키보드, 포커스, 슬라이드 조작, 대체 텍스트
- 반응형: 모바일 360px, 태블릿, 데스크톱
- E2E: 회원 구매, 비회원 구매·조회, 관리자 주문 처리

### 필수 공격·오류 시나리오

- 브라우저에서 가격 변경
- 품절 수량 주문
- 다른 회원 주문번호 직접 접근
- 비회원 주문번호만으로 조회
- 일반 회원의 관리자 API 호출
- 결제 성공 콜백 두 번 호출
- 같은 웹훅 여러 번 전송
- 업로드 확장자·MIME 불일치
- API 또는 DB 일시 실패

### 배포 전

- 운영 빌드와 테스트 통과
- Flyway 적용과 DB 백업
- HTTPS와 인증서 갱신 확인
- CORS·쿠키·CSRF 확인
- 로그에 비밀번호·토큰·개인정보가 없는지 확인
- 재시작 후 DB·이미지 유지 확인
- 직전 정상 버전 롤백 가능
- PostgreSQL 백업 파일을 임시 DB에 실제 복원해 봄
- 외부 모바일 네트워크에서 HTTPS 링크와 로그인 세션 확인
- 배포 30분 이내, 직전 버전 롤백 15분 이내 재현

결함은 P0(보안 노출·데이터 손실·전체 중단), P1(주문·결제·로그인·관리자 핵심 흐름 중단), P2(우회 가능한 부분 문제), P3(문구·장식 문제)로 구분한다. 8월 29일 전달 전 P0와 P1은 반드시 0건이어야 한다.

## 14. 최종 5분 시연

1. 모바일 홈에서 히어로와 상황별 기획전을 확인한다.
2. 상품 상세에서 옵션을 선택해 찜과 장바구니에 넣는다.
3. 비회원 테스트 결제를 완료하고 조회 토큰으로 주문을 조회한다.
4. 로그인해 회원 주문 내역과 찜을 확인한다.
5. 관리자에서 방금 주문과 결제 상태를 확인하고 상품 준비 상태로 변경한다.
6. 상품 가격 또는 홈 기획전 연결을 수정한다.
7. 고객 화면에서 변경 결과를 확인한다.

이 시나리오를 모바일과 데스크톱에서 각각 두 번 연속 성공해야 출시 후보로 승인한다.

## 15. Go / No-Go 기준

### Go

- 회원·비회원 구매가 모두 완료된다.
- 주문·결제·재고 데이터가 DB와 관리자에서 일치한다.
- 타인의 주문과 관리자 API 접근이 차단된다.
- 테스트 결제임이 명확하다.
- HTTPS 링크, 데모 계정, 백업, 롤백 절차가 준비됐다.
- 치명적 오류가 없고 5분 시연을 두 번 연속 성공했다.

### No-Go

- 결제 성공 화면은 나오지만 DB 주문이 없다.
- 중복 결제·중복 재고 차감이 발생한다.
- 가격 변조가 승인된다.
- 회원 또는 비회원 주문 개인정보가 다른 사용자에게 보인다.
- 관리자 권한이 프론트 숨김에만 의존한다.
- 배포 재시작 후 DB나 이미지가 사라진다.
- HTTPS·쿠키 문제로 로그인이나 결제가 불안정하다.

No-Go 항목이 하나라도 있으면 신규 기능과 디자인 수정을 중단하고 구매 흐름 복구를 우선한다.

## 16. 매 작업 세션 운영법

작업을 시작할 때:

1. `README.md`에서 현재 구현과 실행 방법 확인

## 18. 로컬 시연 실행 안내

이 절의 계정·주문·토큰은 `local`/`test` Flyway seed에만 존재하는 명백한 가상 값이다. stage/prod에서 같은 자격 증명을 만들거나 재사용하지 않는다.

### 18.1 최초 준비

저장소 루트의 PowerShell에서 다음을 실행한다.

```powershell
Copy-Item .env.example .env
```

`.env`의 `POSTGRES_PASSWORD`와 `SPRING_DATASOURCE_PASSWORD`를 같은 로컬 전용 값으로 바꾼다. `.env`는 Git에 올리지 않는다. Docker Desktop, Java 21, Node.js/npm이 필요하다.

PostgreSQL은 루트에서 실행한다.

```powershell
docker compose --env-file .env -f .\infra\compose.yaml up -d postgres
docker compose --env-file .env -f .\infra\compose.yaml ps
```

### 18.2 백엔드와 프론트 실행

터미널 1을 저장소 루트에 열고 다음을 실행한다.

```powershell
.\scripts\dev-backend.ps1
```

PowerShell은 현재 폴더 스크립트를 명령 이름만으로 실행하지 않으므로 반드시 `.\`를 붙인다. 이미 `scripts` 폴더로 이동했다면 `.\dev-backend.ps1`을 실행한다. 백엔드는 기본 `http://localhost:8080`, 헬스 확인은 `http://localhost:8080/api/v1/health`다. 첫 기동 때 Flyway V1~V7과 local 반복 seed가 적용된다.

터미널 2를 저장소 루트에 열고 다음을 실행한다.

```powershell
.\scripts\dev-frontend.ps1
```

프론트는 기본 `http://localhost:3000`이다. 의존성이 없다면 먼저 `npm.cmd --prefix .\frontend install`을 실행한다.

### 18.3 local/test 시연 데이터

| 용도 | 값 |
|---|---|
| 일반 회원 이메일 | `demo@example.com` |
| 관리자 이메일 | `admin@example.com` |
| 두 계정의 시연 전용 비밀번호 | `DemoPassword123!` |
| 승인된 회원 주문 | `P20260812-DEMO0001` |
| 실패한 비회원 주문 | `P20260812-DEMO0002` |
| 실패 비회원 주문의 조회 토큰 | `demo-guest-lookup-token-2026` |

비회원 주문 조회는 `/guest-orders`에서 주문번호와 조회 토큰을 함께 입력한다. 조회 토큰 원문은 DB에 저장하지 않고 seed에는 SHA-256 해시만 들어 있다. 실제 주문 토큰은 HMAC-SHA256으로 결정 생성되어 같은 주문 멱등성 키의 첫 응답과 재응답에서 동일하며, 프론트는 URL 대신 sessionStorage로 주문 완료·조회 화면에 전달한다.

추가 시연 데이터는 가상 상품 24개, 옵션 26개, 브랜드 4개, 카테고리 8개, 공개 기획전 3개, 품절 상품을 포함한다. 여러 상품이 자체 제작 이미지 4종을 재사용하므로 실제 판매 자료가 확정되면 교체한다.

### 18.4 추천 시연 순서

1. 비로그인 홈·기획전·상품 상세와 히어로 자동/수동 전환을 확인한다.
2. 상품을 찜·장바구니에 담은 뒤 새로고침해 유지되는지 확인한다.
3. 신규 회원가입은 빈 장바구니·찜으로 시작하는지, 일반 회원 로그인은 방문자 장바구니만 병합하는지 각각 확인한다.
4. 회원 또는 비회원 주문을 만들고 `APPROVE`로 테스트 결제를 완료한다.
5. 별도 주문에서는 `FAIL`을 선택해 실패 상태와 재고 복원을 확인한다.
6. 회원은 `/mypage/orders`, 비회원은 `/guest-orders`에서 조회한다.
7. `/admin/login`에서 관리자 로그인 후 상품·재고·주문 상태·홈 섹션을 확인한다.

### 18.5 로컬 종료와 데이터 유지

프론트·백엔드 터미널에서는 `Ctrl+C`로 각각 종료한다. PostgreSQL만 중지할 때는 다음을 실행한다.

```powershell
docker compose --env-file .env -f .\infra\compose.yaml stop postgres
```

`stop`은 named volume의 DB 데이터를 보존한다. `docker compose down -v`는 local DB 볼륨을 삭제하므로 단순 종료 명령으로 사용하지 않는다.

### 18.6 자동 검증

```powershell
.\backend\mvnw.cmd -f .\backend\pom.xml test
npm.cmd --prefix .\frontend run typecheck
npm.cmd --prefix .\frontend run lint
npm.cmd --prefix .\frontend test -- --run
npm.cmd --prefix .\frontend run build
```

기존 백엔드 PostgreSQL Testcontainers 56개가 통과했다. 2026-08-16 이미지 변경은 백엔드 단위 12/12·compile·package, 프론트 Vitest 17개 파일·55개와 typecheck·lint·production build가 통과했다. 새 targeted 통합 15개는 로컬 Docker engine 부재로 Testcontainers context 생성 전에 차단됐으므로 Docker가 가능한 환경에서 다시 실행한다.

### 18.7 시연과 운영을 혼동하지 않기

- `SIMULATED` 결제는 카드 과금이 없는 시연 기능이다. 실제 PG·웹훅·환불 기능이 아니다.
- local/test 데모 계정·비밀번호·비회원 토큰은 운영 비밀정보가 아니지만 다른 환경에서 그대로 사용하면 안 된다.
- 외부 링크를 열기 전 HTTPS, `Secure` 쿠키, CORS, CSRF, DB 비밀번호, 미디어 영속 경로, 백업·복구를 별도로 확인한다.
- stage/prod는 32바이트 이상의 `GUEST_LOOKUP_TOKEN_SECRET`을 배포 secret으로 주입해야 하며, 누락 시 백엔드가 fail-fast한다. 기존 주문의 멱등 재응답을 위해 값을 임의로 바꾸지 않는다.
- 비회원 조회와 로그인 실패는 stage Nginx에서 우선 속도 제한하며 애플리케이션 계층 제한은 Later다.
- 관리자 이미지 업로드는 구현됐고 물리 삭제·고아 정리·R2/S3 전환, 기획전/분류 CRUD·회원 상세는 Later다.
